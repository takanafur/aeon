## Symptom

`memory/cron-state.json` shows heartbeat with `consecutive_failures: 15`, `last_status: "failed"`, `last_failed: 2026-09-06T05:47:35Z`, `last_success: 2026-09-03T21:23:45Z`. That's ~60h since the last green run — well past the 36h self-check threshold defined in `skills/heartbeat/SKILL.md`. Lifetime `success_rate` still reads 0.95 (277/293) because the failure streak is only ~2.5 days old.

Since `heartbeat` is the only enabled skill in `aeon.yml`, the entire fleet is dark: no logs exist for 2026-09-04 or 2026-09-05, and the public status page has been frozen at "🟢 OK — Updated 2026-09-03 21:23 UTC" the whole time.

## Error signature

The `last_error` field captures a truncated tail of a Claude Code result JSON:

```
"spawned_by_subagents":0,"completed":0,"failed":0,"killed":{"parent":0,"user":0,"system":0}},"is_error":true,"num_turns":1,"su
```

Key signals:
- `is_error: true` — the CLI returned a non-zero result.
- `num_turns: 1` — the agent errored before or during the first model turn (so no tool calls, no partial log).
- `killed.parent/user/system: 0` — not a manual/parent kill; the process failed on its own.

The truncation (200-char cap in the state writer) drops the actual error message that would appear earlier in the JSON payload. Root cause is not yet identifiable from state alone.

## Next steps

- Inspect a recent failed workflow run to recover the full Claude Code output that includes the error message before the JSON summary line (e.g. `gh run list --workflow=... --status=failure` then `gh run view --log`).
- Confirm whether the error is API-side (rate limit, auth), config-side (bad prompt, missing env), or harness-side (parser crash on new SDK version).
- Bump the `last_error` truncation cap in the state writer from ~200 chars to something that preserves the leading error string — 15 failures with the same useless tail is a signal the truncation is cutting off the wrong end of the payload.
- Once root cause is known, dispatch `skill-repair` or open a targeted fix PR.
